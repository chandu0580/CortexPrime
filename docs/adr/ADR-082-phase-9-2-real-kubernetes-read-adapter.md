# ADR-082 — Phase 9.2: Real Governed Kubernetes READ Adapter

Status: Accepted · Date: 2026-08-13 · Phase 9.2 · Follows ADR-081 (capability bridge), ADR-041 (transport), ADR-042 (adapter seam)

## Context

Phase 9.1 proved Kubernetes can be a governed capability — with a scripted provider. Phase 9.2 must prove CortexPrime can safely read REAL Kubernetes state: a real HTTPS request to a real API server, through the ONE existing action path, with no second gateway/executor/credential system/transport, no connector-owned credentials, resourceVersion preserved exactly, and provider failures that never become truth. Discovery (re-verified from source, not reports) established: the sanctioned transport (`TransportBroker` + `HttpxTransportAdapter` + `ProviderChannel`) already performs real provider HTTP for Grafana; the composition seam (`CORTEX_CONNECTOR_FACTORIES` → connector builders constructed with the composition's own broker/policy) already exists; and two 9.1 claims were prose, not code — the `metadata.resourceVersion` normalization did not exist anywhere (the scripted responder pre-baked flat bodies), and the harness reconstructed evidence because `WorkerRuntime.to_execution_result` drops the adapter's `provider_evidence` in one precise projection.

## Decision

**1. The real adapter is a composition of existing parts, not a new one (Part B).** The generic `ConnectorAdapter` + the real 9.1 catalog + a `ProviderChannel` built by `build_kubernetes_channel` against the composition's own `TransportBroker`. No Kubernetes SDK (BND-PROVIDER-SDK stands), no httpx outside `backend.platform.transport` (BND-DIRECT-HTTP stands), no new HTTP client, retry loop, or transport. The channel refuses plaintext outright (a bearer token on plaintext is exposed per request — the GitHub posture, not Grafana's stated dev exception), and the endpoint is deployment configuration with deliberately **no default**: no universal Kubernetes address exists, and a guessed one is a fabricated destination. The model chooses nothing: operation from the binding, path from the catalog's `path_template`, method hardcoded GET, destination from the channel's configured endpoint, credential minted by the broker.

**2. The envelope normalizer is a second narrow port on the generic adapter (Part G).** `evidence()`/`response_problems()` read top-level scalars by design, but Kubernetes nests its continuity token as `metadata.resourceVersion`. Rather than a provider branch in the generic adapter (forbidden by that module's own charter) or nested-path evidence extraction (a bigger contract change), `ProviderBodyNormalizer` mirrors the existing translator port: per-provider envelope understanding lives in the provider's module (`KubernetesReadNormalizer`), applied only on classified success, refusing (never inventing) an envelope it cannot understand. The lift is **exact**: an opaque string, never coerced/hashed/substituted/fabricated. A response with no `resourceVersion` fails the declared required-field check as MALFORMED_RESPONSE — Part N's choice is **reject the observation**, never synthesize. The raw envelope failing the shape check without the normalizer is itself load-bearing: nothing can quietly skip normalization.

**3. One real operation (Part E).** `kubernetes_real_read_catalog()` exposes exactly `kubernetes.pods.list` — the same declared spec (same digest) as the 9.1 contract. The other five stay declared, unexposed until a later phase decides deliberately.

**4. Credentials: the existing composition, unmodified (Part C).** A short-lived (8h), RBAC-scoped (get/list pods, one namespace) ServiceAccount token enters once at the composition root (`CORTEX_KUBERNETES_TOKEN`, the exact `CORTEX_GRAFANA_TOKEN` trust shape) into a `DevelopmentCredentialProvider` (refuses production four ways). The connector never reads the environment; the broker mints per execution for this action digest; the httpx adapter is the only place the credential is read, rendered as one Authorization header. The factory **refuses the scripted/real dual path** (both configured → RuntimeError, Part U: a dual path is a fallback). Phase 5.5 remains blocked and untouched. TLS: the existing `TlsPolicy.ca_bundle_path` (verification is never disabled — there is no `verify=False` in the transport) gains one deployment-config wire, `CORTEX_TLS_CA_BUNDLE`, so a private-CA API server (the disposable k3d cluster) verifies against its cluster CA.

**5. `provider_evidence` survives to the aggregate — one key (Part H).** `WorkerRuntime.to_execution_result` now lifts exactly `provider_evidence` (bounded declared scalars, secret-free by construction) into the published `ExecutionResult.detail`. The rest of the adapter detail stays on the attempt record; the failure path's detail drop is untouched (failures carry their classification via `FailureRecord`). This closes 9.1's honest limitation: the observation leg now reads what actually traversed the pipeline.

**6. The test environment is disposable and least-privilege (Part D).** k3d (`k3d-cortex-p92`, k3s v1.35.5, Kubernetes 1.35), namespace `cortex-p92`, ServiceAccount `cortex-reader` with a Role granting get/list pods in that namespace only (delete refused, other namespaces refused — verified with `kubectl auth can-i`), reached at `https://127.0.0.1:55290` (literal loopback — the broker refuses loopback aliases; 127.0.0.1 is in the API server cert SANs) with the cluster CA as the bundle. Cleanup: `k3d cluster delete cortex-p92`. No production cluster, no developer credentials.

**7. Kubernetes authorization stays distinct from CortexPrime authorization (Part L).** CortexPrime authorizes the attempt; the cluster's RBAC then answers for itself. A real 403 (the SA reading a namespace outside its Role) is classified `AUTHORIZATION_FAILURE` with the cluster's own bounded Status message, the execution FAILS, and no observation/fact exists. It is never a CortexPrime authorization outcome, never UNKNOWN-as-truth, never success.

**8. WATCH is NOT implemented (Part V).** No watch(), no 410 recovery, no bookmarks, no streaming. 9.2 proves only that a real LIST's resourceVersion survives — exactly the handoff point 9.3 needs.

## Consequences

A real Kubernetes read is now a governed CortexPrime capability end-to-end: authorize → lease → gateway → broker-approved HTTPS dial → real API server → normalized bounded evidence → durable aggregate → Phase 7.2 Observation (resourceVersion intact) → Fact → provider-neutral WorldQuery — proven against real Postgres and a real cluster, with real 401/403/TLS/unavailable failures classified and inert, replay inert, four crash points recovered, tenant isolation and the secret firewall holding (the SA token appears in no durable row). Two operational truths surfaced and are recorded rather than hidden: (a) a gateway-refused node returns to READY by design, so a permanently-invalid payload cycles until cancelled — the harness cancels; a production janitor is future work; (b) the scheduler role is a durable 30s lease, so multi-process harnesses must release it (`scheduler.stop()`) or outwait it. This unblocks 9.3 (WATCH on the preserved resourceVersion) and 9.5 (the read-only investigator). No second authority of any kind was created; L1–L16 intact.
